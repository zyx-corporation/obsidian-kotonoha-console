## 1. Purpose

This document defines the RDE audit policy for `obsidian-kotonoha-console`.

RDE stands for Resonant Deviation Evaluator. In this project, RDE is used as a meaning-change audit layer for AI-assisted note transformation in Obsidian.

The purpose of RDE audit is not to judge whether a generated text is simply good or bad. Its purpose is to inspect how the meaning of the original note changes when a proposal is generated, revised, accepted, or rejected.

The central question is:

> What changed in meaning, and is that change authorized by the user's intention, document context, and stated constraints?

## 2. Core Principle

AI-generated text must be treated as a proposal until a human approves it.

RDE audit must help the user understand the semantic difference between the source text and the proposal before applying the proposal to the vault.

The plugin must never silently rewrite user notes.

## 3. Scope

This policy applies to the following operations:

- summarize
- rewrite
- expand
- extract_tasks
- add_metadata
- rde_audit
- any future operation that modifies or proposes to modify note content

The policy applies whether the proposal is generated by a mock backend, local HTTP backend, CLI backend, Kotonoha Orchestrator, or another future backend.

## 4. RDE Categories

RDE audit classifies semantic change using the following categories.

### 4.1 Preserved

`preserved` means that an element from the source text remains meaningfully intact in the proposal.

Examples:

- The original thesis is maintained.
- Key distinctions are preserved.
- Important uncertainty markers remain visible.
- The author's normative stance is not overwritten.
- The original scope is maintained.

### 4.2 Authorized Transformation

`authorized_transformation` means that the proposal changes expression, structure, order, abstraction level, or emphasis in a way that is consistent with the user's request.

Examples:

- A rough memo is reorganized into a structured draft.
- A long paragraph is summarized without changing its core claim.
- A Japanese note is translated into English while preserving uncertainty and intent.
- A technical note is refactored into implementation tasks.

### 4.3 Inferred Extension

`inferred_extension` means that the proposal adds content not explicitly present in the source, but plausibly inferred from context.

Examples:

- A missing implementation step is added.
- A concept already implied by the document is made explicit.
- A likely risk is added as a caution.
- A related term is introduced to clarify the argument.

Inferred extensions are not automatically wrong. However, they must be visible to the user because they are not direct preservation.

### 4.4 Unresolved

`unresolved` means that ambiguity, missing information, conflict, or uncertainty remains after the proposal.

Examples:

- The original instruction is ambiguous.
- The source text contains unresolved contradictions.
- A cited concept lacks enough context.
- The proposal depends on missing external facts.
- A decision cannot be made from the available note alone.

### 4.5 Suspicious Drift

`suspicious_drift` means that the proposal may have shifted meaning beyond what the source text or instruction authorizes.

Examples:

- A possibility becomes a certainty.
- A hypothesis is presented as established fact.
- A political or philosophical stance is narrowed.
- A local design choice becomes a universal theory claim.
- A caution is removed without justification.
- A weak claim becomes a strong claim.

### 4.6 Critical Distortion

`critical_distortion` means that the proposal significantly violates the original meaning, intent, values, authorship, or constraints.

Examples:

- The central claim is reversed.
- The author's position is replaced by an incompatible position.
- The proposal fabricates evidence.
- The proposal attributes claims to the user that were not made.
- The proposal erases essential uncertainty.
- The proposal applies changes that the user explicitly prohibited.

Critical distortion should normally lead to rejection or major revision.

## 5. Required Audit Fields

Every RDE audit result must include the following fields.

```ts
export interface RdeAudit {
  proposalId: string;
  createdAt: string;
  categories: RdeCategory[];
  preservedElements: string[];
  transformedElements: string[];
  inferredExtensions: string[];
  unresolvedElements: string[];
  driftRisks: string[];
  recommendedDecision: "approve" | "revise" | "reject" | "human_review";
  confidence: number;
}
```

The categorical explanation is more important than the confidence value.

## 6. Decision Semantics

RDE may recommend a decision, but the user remains responsible for final approval.

### 6.1 approve

Use `approve` when the proposal preserves the core meaning and any transformations are authorized.

This should only be recommended when there are no significant unresolved issues or drift risks.

### 6.2 revise

Use `revise` when the proposal is useful but contains issues that should be corrected before application.

Typical causes:

- excessive abstraction
- missing uncertainty marker
- minor inferred extension
- incomplete preservation
- wording that changes emphasis too strongly

### 6.3 reject

Use `reject` when the proposal contains critical distortion or serious suspicious drift.

Typical causes:

- central thesis inversion
- false attribution
- unsupported factual claims
- deletion of important constraints
- unauthorized ideological narrowing

### 6.4 human_review

Use `human_review` when the system cannot confidently classify the change, or when domain-specific judgment is required.

This should be common in early versions.

## 7. Audit Workflow

The standard workflow is:

```text
Source Text
    ↓
User Instruction
    ↓
Generation Request
    ↓
Proposal
    ↓
Structural Diff
    ↓
RDE Audit
    ↓
Human Review
    ↓
Approval Decision
    ↓
Apply or Reject
    ↓
Audit Log
```

The vault must only be modified after the approval decision.

## 8. Structural Diff vs RDE

Structural diff and RDE are different.

Structural diff identifies surface-level changes such as additions, deletions, and replacements.

RDE interprets the semantic significance of those changes.

For example:

```text
Source:
This may be possible.

Proposal:
This is clearly true.
```

A character-level diff may look small. RDE must classify this as a possible suspicious drift because uncertainty was removed.

Another example:

```text
Source:
RDE can evaluate AI outputs.

Proposal:
RDE can evaluate meaning changes in collaborative thinking between humans and AI.
```

This may be an authorized transformation or inferred extension if the surrounding context supports that broader claim.

## 9. Special Drift Patterns

RDE audit should explicitly check for the following drift patterns.

### 9.1 Claim Strength Drift

A weaker claim is transformed into a stronger claim.

Examples:

- may -> must
- possible -> certain
- suggests -> proves
- hypothesis -> fact
- design direction -> completed system

### 9.2 Evidence Drift

A proposal makes evidence appear stronger than it is.

Examples:

- Unverified observation becomes established data.
- Personal interpretation becomes cited fact.
- Draft argument becomes research conclusion.

### 9.3 Scope Drift

A limited claim becomes universal.

Examples:

- This implementation may work for the MVP.
- This is the correct architecture for all Kotonoha systems.

The second statement is stronger and broader than the first.

### 9.4 Responsibility Drift

The proposal changes who is responsible for judgment or action.

Examples:

- Human approval is replaced by automatic execution.
- AI recommendation is presented as final decision.
- Audit assistance becomes authoritative judgment.

### 9.5 Ideological Narrowing

The proposal narrows or domesticates the user's philosophical, political, or design stance.

Examples:

- A structural critique becomes a neutral productivity statement.
- A relation-based theory becomes a conventional tool description.
- Institutional responsibility is reduced to personal preference.

### 9.6 Implementation-Theory Substitution

A practical implementation shortcut is presented as a theoretical claim.

Examples:

- A temporary schema becomes a formal ontology.
- A mock RDE implementation is treated as the RDE theory itself.
- A UI decision is mistaken for a governance principle.

### 9.7 Authorship Drift

The proposal makes the AI appear to own or finalize the user's thought.

Examples:

- Rewriting removes the author's distinctive stance.
- The proposal speaks as if the user's intention is fully known.
- Generated extensions are not marked as generated or inferred.

## 10. Audit Display Requirements

The UI should display RDE audit results using explanatory sections, not only badges or scores.

Required display sections:

- Preserved elements
- Transformed elements
- Inferred extensions
- Unresolved elements
- Drift risks
- Recommended decision
- Confidence and uncertainty note

The UI should avoid implying that a high confidence score means the proposal is safe.

## 11. Logging Policy

Each proposal and audit should be logged under `.kotonoha/`.

Recommended layout:

```text
.kotonoha/
├─ proposals/
│  └─ 2026-05-29T000000+09-00.proposal.json
└─ audit/
   └─ 2026-05-29T000000+09-00.rde-audit.json
```

### 11.1 Default Log Mode

Default mode should be `summary`.

It should include:

- schema version
- plugin name
- created timestamp
- file path
- operation kind
- source hash
- proposal hash
- short source excerpt
- short proposal excerpt
- RDE categories
- recommended decision
- human decision if available

### 11.2 Hash-Only Mode

Hash-only mode should include:

- source hash
- proposal hash
- metadata
- audit categories
- human decision

It should avoid storing text excerpts.

### 11.3 Full-Text Mode

Full-text mode may store source and proposal text, but it must be opt-in.

This mode is useful for reproducible research and full semantic lineage, but it may expose private note content.

## 13. Backend Contract

A Kotonoha or RDE backend may return audit results directly.

Recommended response shape:

```ts
export interface KotonohaProposalResponse {
  proposal: Proposal;
  audit?: RdeAudit;
}
```

If the backend does not provide RDE audit, the plugin may:

1. show the proposal without audit,
2. run a local rule-based audit,
3. call a separate RDE backend,
4. ask the user to perform manual review.

The plugin must not pretend that an audit was performed when it was not.

## 14. Minimum Rule-Based Audit for MVP

Before a full RDE engine exists, the plugin may implement a minimal rule-based audit.

Initial checks:

- Detect uncertainty weakening:
  - "may" to "is"
  - "possible" to "certain"
  - "hypothesis" to "fact"
- Detect deletion of frontmatter.
- Detect deletion of citations or links.
- Detect large reduction in text length for rewrite operations.
- Detect generated claims containing URLs or dates not present in source.
- Detect removal of explicit human approval language.
- Detect conversion from proposal language to final decision language.

These checks are not a substitute for RDE, but they provide useful guardrails.

## 15. Human Approval Requirements

Before applying a proposal, the UI must show:

- source target: full note or selected range
- operation kind
- user instruction
- proposal text
- RDE audit summary if available
- warning if audit is missing
- Apply, Revise, Reject, and Copy actions

The default action should not be Apply.

## 16. Handling Missing or Uncertain Audit

If RDE audit is unavailable, the plugin should display:

```text
RDE audit is not available for this proposal.
Review carefully before applying.
```

If RDE audit confidence is low, the plugin should display:

```text
RDE audit confidence is low.
Human review is required.
```

Low confidence should normally map to `human_review`.

## 17. Privacy Requirements

RDE audit may expose sensitive note content.

The plugin must:

- make backend mode visible
- disclose whether text is sent outside the local machine
- allow mock/local mode
- default to summary log mode
- make full-text logging opt-in
- avoid sending the whole vault unless explicitly requested
- avoid background transmission without user action

## 18. Failure Handling

If generation or audit fails:

- do not modify the note
- show an error message
- preserve the source text
- avoid creating misleading approval logs
- optionally write an error log with metadata only

If apply fails:

- preserve the proposal
- report that the note was not modified
- do not mark the decision as approved unless the write succeeded

## 19. Relation to SLS

RDE audit logs are not the full Semantic Lineage System.

However, they should be compatible with future SLS integration.

The audit log should therefore preserve:

- source hash
- proposal hash
- operation kind
- semantic categories
- decision
- timestamps
- file path
- optional excerpts or full text

Future SLS integration may treat each approved proposal as a semantic transition event.

## 20. RDE Self-Audit of This Policy

### Preserved Elements

This policy preserves the idea that RDE evaluates meaning change rather than surface quality or simple safety.

### Authorized Transformations

The general RDE framework is transformed into operational rules for an Obsidian plugin.

### Inferred Extensions

The minimal rule-based audit checks, log modes, and backend response shape are implementation-oriented extensions.

### Unresolved Elements

The full RDE scoring algorithm, calibration process, and integration with Kotonoha Orchestrator remain unresolved.

### Drift Risks

There is a risk that a rule-based MVP may be mistaken for the full RDE theory. The UI and documentation must clearly mark MVP checks as provisional guardrails.

### Next Update Policy

The next update should create TypeScript definitions and initial tests for RDE categories, audit parsing, and audit log writing.
